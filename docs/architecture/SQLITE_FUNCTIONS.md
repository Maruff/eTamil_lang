# eTamil functions in SQLite queries: the plan for the compiler

**Status: built** (WBS 1.20, in 2.0), in the order below. It turns the spike on
`spike/sqlite-functions` (`eTamil_sqlite/`, which uses only the compiler's public API and
changes nothing in it) into a feature of the compiler. The builtin is `தளம்_செயல்_பதிவு`,
the code is `src/purity.rs`, `src/db/function.rs` and the `register_function` hook in
`src/db/`, the tests are `tests/sqlite_functions.rs`, and the sample is
`examples/db_samples/qaLam_ceyal_paqivu.qmz`. **Still open:** a Tamil reader's review of
the builtin's name and of the Tamil text in its error messages (the messages from the
purity check are English only), and PostgreSQL and MySQL, which refuse.

What the user gets:

```
செயல் moqqam_vari(qokY, vikiqam) {
    திரும்பு qokY * (1 + vikiqam / 100);
}

தளம்_இணை "SQLite" ":memory:"
தளம்_செயல்_பதிவு("moqqam_vari", moqqam_vari, 2)
rows = தளம்_வினவு("SELECT eN, moqqam_vari(qokY, 18) AS moqqam FROM paRRuccIttu")
```


The spike measured **about 5.8 microseconds a row** and showed exact decimals, Tamil names, runtime
errors becoming SQL errors, and the step limit all work. What is left is the compiler plumbing.

## The pieces, in the order they will be built

Each is a separate commit with its own tests, so any one can be reviewed or dropped.

1. **The VM keeps the running program's bytecode.** `execute` takes the `Bytecode` by value and
   forgets it. A function value is only a name plus captured values (`FunctionValue`); its body
   lives in `Bytecode::functions`. To call one later, from a SQLite callback, the VM needs to
   hold the bytecode behind an `Arc`. No behaviour change; checked by the whole existing suite.
2. **A purity check on compiled code, in the compiler.** The spike's allowlist
   (`eTamil_pg/eval`) walks the syntax tree and uses a list of safe builtins generated by a
   `build.rs` from `interpreter.rs`. At run time there is no syntax tree, only `Instruction`s,
   so the check walks the instructions of the function and of every function it can call. It
   refuses `FileOpen`, `FileClose`, `FileWrite`, `FileRead`, `ReadCSV`, `WriteCSV`, `DBConnect`,
   `DBDisconnect`, `DBQuery`, `DBExecute`, `DefineRoute`, `SendResponse`, `SendJSON`,
   `StartServer`, `Input` and imports, and any `Call` to a builtin not on the safe list.
   `FunctionInfo` records only where a body starts, not where it ends, so the walk needs the
   end: the jump that skips the body precedes `start`. This is the riskiest piece and gets the
   most tests, including every refused instruction and a call that reaches a forbidden one
   indirectly.
3. **`Database::register_function`**, optional and defaulted to "not supported". Only the SQLite
   driver implements it, with `rusqlite`'s `functions` feature (not enabled today). The callback
   builds a fresh VM per call, binds the arguments, runs under a step limit, and converts the
   result, as the spike does.
4. **The builtin** that registers a function value on a named connection, and the rule for
   pooled connections: **register again after every `தளம்_இணை`**, which replaces the old
   definition. A function registered on a pooled connection otherwise outlives the request that
   made it, and a later request could call a stale one.
5. **Documentation, a sample under `examples/`, and the counts.** A new builtin moves the
   builtin count the site and README guard, so the same commit updates them and
   `scripts/check_site_counts.py --check` must pass.

## Names

The builtin follows the same standard as every other: **three spellings**, in the form the
database builtins already use (`தளம்_செய்_முயற்சி | qaLam_cey_muyaRci | _tryExecute`).

| Spelling | Name | Where it comes from |
|---|---|---|
| Tamil | `தளம்_செயல்_பதிவு` (database, function, register) | the `தளம்_` prefix of the database builtins, and `செயல்`, the keyword for a function |
| Latin transliteration | `qaLam_ceyal_paqivu` | the output of `scripts/transliterate.py`, not written by hand |
| English | `_registerFunction` | a leading `_` and camelCase, as `_tryExecute`, `_tryQuery` and `_redisConnect` have; the underscore marks it as English (`docs/reference/SCRIPT_RULES.md`) |

It is checked the same way the others are: `scripts/check_script_rules.py` for the underscore
rules, `generate_editor_support.py --check` so the editors' completion lists include it, and
`scripts/check_site_counts.py --check` for the builtin count. The Tamil word choice is still for a
Tamil reader to confirm before it merges, and it is cheap to change until the count is committed.

## Names of files, folders, tables and fields

The sample, its file and folder names, the database, its tables and their columns use the
ezuqqu romanization, as the rest of the project does: `qokY` (தொகை, amount), `vikiqam` (விகிதம்,
rate), `moqqam` (மொத்தம், total), `paRRuccIttu` (பற்றுச்சீட்டு, invoice), `eN` (எண், number),
each produced with `scripts/transliterate.py`. The audit is `scripts/check_names.py --check`, which
runs in CI and must stay at 0 names off-scheme; names that are English by necessity are listed in
its `ALLOW` list, not renamed.

## Rules the spike found, kept as they are

- SQLite orders TEXT after every number, so an exact (text) result makes `WHERE f(x) > 500` true for
  every row. Two modes: exact text (default) and numeric (`INTEGER` when whole, else `REAL`).
- `SUM` over exact text is a float in SQLite. To stay exact, sum in eTamil.
- A function's name has to be legal in SQL and in eTamil (`add` and `nothing` are SQL keywords).

## Not in scope

PostgreSQL and MySQL functions from a program (they say "not supported"); aggregate and window
functions; registering from a file the program does not define; and caching a VM between calls,
which would risk leaking state between rows.
